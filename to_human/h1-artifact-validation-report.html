3. 关键机制：Artifact 是消费者界面

H1 的进一步验证将“文件”重新解释为“消费者界面”。每个 artifact 的存在不是因为项目目录需要整齐，而是因为某类消费者需要在未来某个时刻读取某种压缩级别的信息，并据此采取行动。

Artifact 设计问题：
1. 谁会消费它？
2. 消费者需要原始数据、操作状态、综合认知，还是展示叙事？
3. 它支持什么决策或下一步行动？
4. 如果没有它，研究系统会失去什么能力？

4. Artifact 层级栈

Raw evidence layer
  data/, logs, result files

Protocol and reproducibility layer
  experiments/*/protocol.md, analysis.md

Operational state layer
  research-state.yaml

Cognitive synthesis layer
  findings.md

Governance and communication layer
  to_human/*.html or *.pdf

Final contribution layer
  paper/

5. 为什么不能只靠聊天记录？

纯聊天记录不适合作为长期研究的主要载体，因为它同时存在五个问题：

  • 线性：状态、证据、结论、报告混在一条时间线上。
  • 依赖上下文窗口：长程信息会压缩、丢失或难以恢复。
  • 消费者未分化：AI 的操作状态和人类的阅读报告混在一起。
  • 审计性弱：协议、结果和 pivot 不容易作为独立对象检查。
  • 恢复困难：未来循环需要简洁状态，而不是完整对话。

6. 可复用设计原则

原则：长期 AI 技能的每个持久化 artifact 都应声明消费者和决策功能。

Artifact: <名称>
Producer: <谁创建/更新>
Consumer: <谁读取>
Compression level: <raw / operational / synthesized / presentation>
Decision enabled: <它支持什么行动>
Failure if missing: <没有它会坏掉什么>

这意味着 artifact 设计本质上是交互设计，而不仅是文件组织。

7. 下一步

建议继续验证 H2：人机协作是否可以稳定解释为“不对称生产者/消费者交换”。下一轮可以把该模型与三种替代模型比较：

  1. 命令执行模型：人逐步下命令，AI 被动执行。
  2. 委托模型：人给目标，AI 交付结果，但中间缺少治理 artifact。
  3. 审批流模型：AI 每一步都请求确认，安全但低效。
